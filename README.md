# 魔兽多角色看板（WowAltBoard）

[![许可 MIT](https://img.shields.io/badge/许可-MIT-blue?style=flat-square)](LICENSE)
[![赞赏 爱发电](https://img.shields.io/badge/赞赏-爱发电-946ce6?style=flat-square)](https://ifdian.net/a/lianzy)

把游戏里插件存下来的数据汇总成一个本地网页：**所有战网账号、所有角色**的大秘境、宝库、
地下堡、藏宝图、团本、纹章、猎物、装备、金币、专业，一张表里横向对比。

主体数据来自 **AlterEgo**；**专业**来自 BagSync，**备份箱**来自 MySlot 和编辑模式缓存 ——
后两者都是可选的，装了就多几列，没装就少几列，其余功能一个不少。

不用开游戏，不用服务器，整个文件夹可以拷到任何地方（U 盘、别的电脑）直接用。

## 安装

**不需要装任何环境。** 解压，双击 `魔兽看板.exe`，完事。

Windows 10/11 自带这个工具需要的全部东西：PowerShell 5.1、.NET Framework 4.x、
一个 Chromium 浏览器（Edge 是系统组件）。所以没有做 .msi / setup.exe：安装包只会带来
开始菜单和「添加/删除程序」条目，代价是杀毒软件更敏感，还破坏了「整个文件夹拷到哪都能用」
这个本来的特点。想要桌面图标的话，托盘菜单里有「创建桌面快捷方式」。

页面用**你的默认浏览器**打开（只要它是 Chromium 系：Edge / Chrome / Brave 等），
开的是无地址栏的 app 窗口。这样页面里点出去的链接也落在同一个、也就是你惯用的浏览器里。
默认浏览器是 Firefox 时会退回 Edge 或 Chrome —— Firefox 不支持 `--app=`。

发布包用 `tools/build-release.ps1` 打，产物是一个 zip，作为 GitHub Release 附件分发。

## 用法

双击 **`魔兽看板.exe`**。它是一个独立程序，不是快捷方式：

1. 扫描游戏目录，期间显示一个小进度窗口。扫不出数据时弹一个中文对话框，说明是哪一种情况、
   下一步该做什么，并且带「重新扫描」按钮 —— 按提示去装插件 / 进游戏 `/reload` 之后，
   不用重开程序，回来点一下就行（见「扫描失败了怎么办」）
2. 以 **应用模式**（`--app=`）打开看板 —— 没有地址栏和标签栏，有自己的任务栏图标，
   看起来就是一个独立软件，但底层还是 Chromium，页面效果不打折
3. **常驻托盘**，盯着游戏的 SavedVariables。你在游戏里 `/reload` 或退出角色之后，
   它会自动重新扫描并弹一个气泡提示

托盘图标右键：打开看板 / 立即重新扫描 / **设置游戏目录** / 创建桌面快捷方式 / 退出。
不想让它常驻就选退出。

**只会有一个实例。** 再双击 exe 不会多出一个托盘图标，而是把已经打开的看板窗口拉到前面
（没开就开一个）然后自己退出。用命名 Mutex 判断，退出时释放，所以从托盘退出后还能正常再启动。

「设置游戏目录」是个文件夹选择框，选完直接写进 `tools/config.json` —— 自动探测失败时
不用手改 JSON。默认只读**正式服**（`_retail_`），要连 classic 一起读就在 config 里把
`includeFlavors` 改成 `[]` 或列出想要的版本。

页面右上角还有「刷新」按钮和「自动」开关（每 30 秒重载一次），配合托盘的自动重扫，
打完本切出来就能看到新数据。

`启动.bat` 做的是同样的扫描，但会开黑色控制台窗口显示完整过程 —— 排查问题时用它。
如果杀毒软件把 exe 隔离了（新编译的程序有时会被误报），也用 bat。

exe 是用 `tools/build-launcher.ps1` 现场编译出来的：C# 编译器随 .NET Framework 装在
Windows 里，不需要装任何开发工具。改了里面的 C# 之后重跑那个脚本即可。

为什么不做成真正内嵌浏览器的程序：WebView2 的运行时不能从这里分发，而 .NET 自带的
WebBrowser 控件是 IE11 内核，渲染不了这个页面（CSS 变量、flex gap、position sticky 都不支持）。
应用模式是在「零依赖」前提下最接近独立程序的做法。

* 点表头排序；**按住表头左右拖动**可以换列的位置，拖分组表头可以整组搬家，见「列的顺序和布局方案」
* 「布局方案」：把调好的列顺序 / 显隐存成命名方案，顶栏下拉一键切换；
  存的时候「同时记住筛选和外观」默认勾着，那种方案切过去连最低等级、皮肤、字号一起换
* 点任意一行看该角色的完整明细（逐本最佳记录、宝库三档、装备 16 槽位、狩猎清单）
* 「设置」分成六个标签页：布局 / 筛选 / 数据 / 列 / 外观 / 其他，只渲染当前那一页，
  记住你上次停在哪个标签
* 「周趋势」：按游戏周对比评分、装等、宝库、藏宝图
* 「备份箱」：MySlot 导出串、编辑模式缓存，以及你自己贴进去的任何插件导入串
* 「导出 Excel」：导出当前屏幕上显示的列和行。旁边的 ▾ 里收着「导出 CSV」和「打印 / PDF」
* 抽屉和面板：点面板外面、按 Esc、或点「关闭」都能关掉
* 标题栏有深浅切换（深色/浅色分段按钮）、刷新、自动刷新
* 窗口和任务栏用的是看板自己的图标（`app/icon.svg`，和 exe 的图标同一个样式），
  不再是浏览器的默认图标
* 「显示的列」里每个分组都有全选 / 全不选，顶上还有「全部显示」「只留基础」；
  这些批量按钮只改复选框，不重建面板 —— 滚动位置和展开的分组都留在原处
* 「专业」列：装了 BagSync 才有，见「专业列」一节
* 「赞赏」：爱发电页面的入口（设置最底下）
* 关掉看板窗口时，启动器可以跟着退出或留在托盘 —— 第一次关会问一次并记住，
  之后在托盘菜单「关闭看板时」里改
* 窗口位置和大小会记住，下次开在原地（最大化状态也记）
* 导出 / 复制 / 保存设置都会在右下角弹一个 3 秒的提示，导出的提示里带完整路径和「复制路径」
* 「注意」和「更新」都是可关闭的横幅；更新提示按版本号记住关闭状态，下个版本会重新提醒
* 标题栏右侧始终显示看板版本号（鼠标悬停还能看到插件版本、扫描时间、最新发布版本）——
  报问题时先把这个发过来

`tests.html` 是离线自测页，134 项解析器、数据回归与毕业装备测试，出问题时先看它。
命令行也能跑，还多五项浏览器里做不到的检查（图标文件在不在、天赋树画没画出来、
天赋树的方块有没有重叠或跑出画布、无障碍属性齐不齐、两份生成数据的格式合不合）：

```
node tools\run-tests.js
```

## 列的顺序和布局方案

**表头直接拖。** 按住一个列标题左右拖，它就在自己的分组里换位置；按住分组表头
（`大秘境` / `宝库` 那一行）拖，整组左右搬家。点一下仍然是排序 —— 移动超过 5 px 才算
拖动，拖完的那一次 click 会被吃掉，所以两个操作不会互相干扰。

**只能在组内换位置，这是故意的。** 分组表头那一行是靠「同一组的列必须连续」才成立的：
一个被拆成三段的分组需要三个表头格子，而 colSpan 一旦算错，症状就是
「宝库的数据跑到大秘境下面」。所以拖过组边界时不会拒绝你，而是**夹到本组的边缘** ——
拖动时的插入标记会一直告诉你它最终会落在哪。

**冻结的那一列跟着走。** 以前是硬编码冻结「角色」列，现在任何分组都能拖到最前面了，
所以改成冻结**最左边那个可见列**：把「金币」整组拖到最前，冻结的就是金币；把首列取消
勾选，冻结自动顺延到下一列。

**布局方案存的是整个视图**：分组顺序、每组里的列顺序、哪些列隐藏，
外加最低等级、隐藏的角色 / 服务器 / 账号、皮肤、明暗、字体、字号。
保存时的「同时记住筛选和外观」**默认是勾上的** —— 大家嘴里的「布局方案」基本都指
当时整套看法，存回来却少了筛选和皮肤，比多带上更让人意外。不想要就把勾去掉，
那个方案就只管列。**是逐个方案的属性，不是全局开关** —— 每一行都标着自己存了
什么（`列` 还是 `列 + 筛选 + 外观`），「覆盖」也保持这一行原本的类型，不会把一个只管列的
方案悄悄升级成会搬走你筛选的方案。排序始终不算在内。
设置最上面的「布局方案」里可以保存 / 应用 / 覆盖 / 重命名 / 删除；存过至少一个之后，
标题栏右边会多出一个下拉，一键切换。当前表格和某个方案完全一致时下拉就显示那个名字，
你一动列它就变成「当前（未保存）」—— 这个状态是每次实时比出来的，不是记个标记，
所以不会出现「明明改了还显示着旧方案名」。

**顺序是「部分」保存的。** 方案里没提到的列 id 保持注册表里的相对顺序、排在提到的之后；
提到但已经不存在的 id 直接丢掉。所以上个赛季存的方案在新赛季照样能用，不会把它没听说过
的新列（新赛季的副本、刚出现的专业）弄没。

**同时优先认上次切的那一个。** 两个方案完全可能在窄的那个的口径上无法区分 ——
一个只管列的方案，只要列对得上就算命中，不管另一个宽方案把筛选改成了什么。按数组顺序
取第一个命中的，就会让宽方案看起来“根本切不过去”：你选了方案3，筛选和皮肤确实变了，
可标签弹回了方案1。所以先看上次应用 / 保存的那个还算不算命中，不算了才往下找。
这一条有四项回归测试守着。

**「当前（未保存）」是比出来的，不是记出来的。** 有没有命中某个方案，是每次拿实时状态和
各个已存方案按**它自己的类型**比一遍得出来的：改筛选不会让一个只管列的方案脱钩，改列才会。
这样就不需要每条改动路径都记得去失效一个「当前方案」标记，也不会出现「明明改了还显示着
旧方案名」。

**设置面板分六个标签页。** 十一段内容塞在 380px 宽的抽屉里，要滚过十六个角色的复选框才
看得见「显示的列」。现在按 布局 / 筛选 / 数据 / 列 / 外观 / 其他 分开，**只构建当前那一页** ——
看列表的时候不用为角色列表付代价。滚动位置按标签分别记，切回来还在原处。

## 专业列（需要 BagSync）

**AlterEgo 不记录专业。** 它的 SavedVariables 里没有任何 profession / skillLine 字段，
源码里 `Professions` 只出现在制作品质星级的图标字符串里。所以专业不可能从 AlterEgo 来。

BagSync 记录了。装了 BagSync 之后重新扫描，表里就会多出「专业」一组：
**专业 1 / 专业 2**（主专业，格子里是名字 + 当前资料片的技能等级）和 **烹饪 / 钓鱼**
（只有真的有人学过才会出现这一列）。没装 BagSync 的话这一组列压根不生成，
设置 → 显示的列 底下会有一行提示和下载地址。不想读就把 `tools/config.json` 的
`readBagSync` 改成 `false`。

BagSync 的存档单独放在 `data/bagsync.js`，不塞进 `data.js` —— 那些文件每个 14～165 KB，
绝大部分是背包 / 银行 / 邮箱内容，跟专业无关，没装的人不该为此付代价。

两个人和数据对着干过的地方：

**join 用 GUID，不用「名字 + 服务器」。** BagSync 的每个角色都存了
`guid = "Player-707-XXXXXXXX"`，和 AlterEgo 的 `global.characters` 用的是同一个键。
这台机器上真有三个同名角色，按名字 join 一定串。

**「当前资料片的等级」比看起来难取。** 专业顶层大多没有等级，等级在
`categories` 里按资料片分段。两个想当然的规则实测都是错的：

* **按 `orderIndex` 取 1** —— 它既不唯一也不总是最新。烹饪有六条经典旧世的
  「之道」子技能全都是 `orderIndex 1`，和 `至暗之夜料理` 挤在一起；炼金术里
  `卡兹阿加` 是 1 而 `至暗之夜` 是 2
* **把 `categories` 全当技能线** —— 里面大部分是叶子子分类（零件 / 爆炸物 /
  `附录 I - 术语`），根本没有等级字段。把缺失的等级当成 0，一个满级工程师就显示成
  「工程学 0」——第一版就是这么错的

真正管用的是 **分类 ID 按内容上线顺序发放**：在带等级的分类里取 ID 最大的那个，
就是最新资料片。本机所有同时带 BagSync 自己顶层等级的记录都拿来对照过，8 比 0 一致。
顶层有值时优先用它（那是 BagSync 自己算的），本机有 26 条记录没有顶层值，
所以 ID 规则必须存在。

**主专业 / 副专业的划分是硬编码的**（`app/labels.js`），因为 BagSync 存的是一张没有
槽位顺序的哈希表，游戏本身也没把「第一/第二专业」写进硬盘。不在这两张表里的技能线
会被丢掉，已知的就是 `794 考古学`：正式服 11.0 已经移除，BagSync 还留着旧记录，
一列永远 1/800 的考古学纯属噪音。

## 毕业装备 / 天赋（顶栏「毕业装备」）

数据来自 **GearInsight** 插件自带的静态参照表（作者：枫叶大象-格瑞姆巴托/yinpeng，
数据源是 WarcraftLogs 顶尖玩家记录）。**已经预转换好打进包里了，不用另外下载，
也不需要装插件。**

面板里有什么：

* **40 个专精**（13 个职业 × 3～4 专精），按 `职业 → 专精` 两行按钮选
* **每个部位 2～3 件候选**，带装等、掉落来源、副属性、**使用率**（多少比例的顶尖玩家在用）、
  可升级上限，以及**升级轨道**（「英雄 6/6」这种，见下）
* **两套视角**：团本 / 大秘境。同一个专精两套推荐是不一样的，切换按钮在顶部
* **和你自己的角色对照**：选一个角色，每个部位会显示你身上那件，对上了标绿，
  底部给「对上 N 件，差 N 件」
* **属性目标**（暴击/急速/精通/全能的目标百分比，三套：团本 / 冲分 / 割草）、属性权重、
  毕业装等、武器形态分布
* **宝石 / 附魔 / 消耗品**，附魔按部位分，都带使用率
* **每个部位标题上的「记录 xx%」**：这几件加起来占顶尖玩家的多少。
  低于 50% 会标黄 —— 意思是“剩下一半人穿的东西不在这份数据里”，看下面那节
* **天赋**：WCL 前五名的真实天赋，按团本 / 冲分 / 割草分类，给出热门套路的点数分布、
  英雄天赋占比、以及每套是谁在用（玩家名 / 服务器 / 地区）
* **画出来的天赋树**：职业 / 专精 / 英雄三块，点了的节点和连线高亮，多段天赋显示 `2/3`，
  鼠标放上去给全名、二选一的选项、层级要求。节点名是**暴雪 zhCN 客户端自己的串**，见下

### 这份数据有多可信（实测数字，别只看百分比）

面板里每个百分比看起来都很确定，但底下这几条是我把整份数据统计一遍量出来的，
**在信它之前先知道这些**。

对得上的部分：

| 检查 | 结果 |
| --- | --- |
| 大秘境副本 | 8 个，和本机赛季 18 的 `challengeModeID` 一一对应（数据用的是 `journalInstanceID`，两套编号指同 8 个副本） |
| 团本 | 烈毒之渊，`instanceId` 1320，就是当前团本 |
| 每部位使用率之和 | 从不超过 100%（最大 100.1，浮点误差） |
| 同一部位内重复 itemId | 0 组 |
| 戒指 1/2 列表相同 | 80 组里 0 组（说明不是简单复制） |

需要打折扣的部分：

* **完全没有样本量。** 「81%」背后是 5 个人还是 500 个人，数据里查不到 ——
  原始 Lua 就没有这个字段，不是转换时丢的。这一条**改不了**，只能换数据源。
* **列表是截断的。** 1264 个部位组里，使用率之和的中位数只有 **72.9%**，
  **206 组不到 50%**，最低 8.6%。也就是说很多部位「剩下一半人穿什么」不在数据里。
  面板每个部位标题上那个「记录 xx%」就是这个数，低于 50% 会标黄。
* **属性权重是硬编码的，不是模拟出来的。** 40 个专精只有 38 种不同组合，
  取值全部量化到 0.1 的档（0.3～1.0）。当粗略排序用可以，别拿它算收益。
* **饰品栏有 1/80 组两个格子完全相同**（可疑，但只有一组）。
* 66 件低 itemId 的装备（158366～159255）来自塞塔里斯神庙 / 诸王之眠 / 红玉新生法池 ——
  **这不是脏数据**，旧副本进 M+ 池仍然掉原来的物品。

所以这份数据适合回答「大家都在穿什么」，不适合回答「我该穿什么最优」。
面板的脚注里也写了同一句话。

**那为什么不换一家？** 找过，本机能走通的没有：

| 站点 | 结果 |
| --- | --- |
| archon.gg / warcraftlogs.com / u.gg | **403**，Cloudflare 拦的，直连和代理都一样 |
| murlok.io | 能访问，但**只有 PvP（3v3 竞技场）**，没有大秘境/团本页面 |
| bloodmallet.com | 能访问，JSON 接口公开，**但给的是模拟 DPS 不是使用率**，而且只覆盖饰品、副属性配比、种族、药水，装备槽位没有 |
| raidbots.com | `bonuses.json` 能直连拿到（1.7 MB），是一份 bonusID 词典，**没有任何装备推荐** |

bloodmallet 有一点是这份数据没有的：它写明了 `iterations: 60000` 和 `target_error: 0.1`，
也就是**有样本量**。但它是模拟器结果，回答的是另一个问题。

换句话说，「换个带样本量的来源」目前做不到，所以这里的做法是**把缺陷标在明面上**
（每个部位的「记录 xx%」徽章 + 上面这张表），而不是假装数据很确定。

### 天赋树能画出来了，中文名来自暴雪自己的数据表

**这一节以前写的是「画不出来」。现在能画了 —— 变的不是插件，是数据来源。**

插件里存的天赋只是 **`entryID` + 点数**，例如 `{96167: 1, 96170: 2, ...}`：
**没有节点名称、没有图标、没有坐标、没有连线关系。** 两个插件的 30 个文件全搜过，
唯一跟树结构有关的字眼是 `TalentExport.lua` 注释里出现过一次的 `treeHash`。
插件在游戏里能显示天赋，是因为它调**游戏运行时的 `C_Traits` 接口**现查
（`GetTreeNodes` / `GetNodeInfo` / `GetEntryInfo`），网页里没有这些接口。

缺的那一半从两个公开来源补上，本机实测**都能直连**（不用代理）：

| 来源 | 拿到什么 |
| --- | --- |
| `raidbots.com/static/data/live/talents.json`（3.2 MB） | 40 个专精的完整树：节点坐标、连线、层级要求、每个节点的 `entryID` / `spellId` / 图标名 |
| `wago.tools/db2/<表>/csv?locale=zhCN`（约 11 MB） | 暴雪 DB2 原表的**中文名**：`TraitDefinition` / `SpellName` / `TraitSubTree` |

两边靠 `entries[].id` 对接，而它**就是**插件里那个 `entryID`：40/40 个专精的 specID 对得上，
手里 3040 个 entryID 有 3039 个在树里找得到，**38/40 个专精 100% 命中**。

中文名的链路是 `definitionId → TraitDefinition.ID → OverrideName_lang`，
没有就退到 `SpellID → SpellName.Name_lang`。实测 **5387/5387 = 100% 有中文**，
没有一条回退到英文 —— 面板上的「斜掠」「狂暴回复」「能量枢纽」都是
**暴雪 zhCN 客户端自己的串，不是我翻的**。生成器在中文覆盖率低于 95% 时直接报错退出，
宁可不产出，也不产出半英文的树。

顺带把**英雄天赋的名字也修了**：以前面板里 39 个英雄天赋全是英文（`Deathbringer`、
`San'layn`），因为插件存的就是英文。现在靠 `TraitSubTree` 的中文名对上去，39/39 全中，
显示成「死亡使者」「萨莱因」。

生成命令（只在**打包前**跑，用户运行时完全不联网）：

```
node tools\fetch-talent-tree.js
```

产出 `app/talent-tree.js`（415 KB，随包发）。它是**可选的** —— 加载不到就退回
「只有统计、没有树」的旧样子，功能不受影响。

面板上画三块：职业树 / 专精树 / 英雄天赋。点了的节点高亮，连线也高亮，
多段天赋显示 `2/3`，鼠标放上去给节点全名、二选一的两个选项、层级要求。
顶上的「套路」按钮按人数排序，可以切着看不同套路点在哪。

**节点上没有图标，这是故意的。** 全部天赋图标是 2094 张、约 4.6 MB，
是现在整个发布包（1.6 MB）的三倍。坐标、连线、中文名、点数都在，
不带图标一样读得懂，所以先不带。

**坐标为什么不是直接缩放的**：上游 `posX/posY` 的最大公约数只有 10，还存在
「相差 10」的近重复坐标，直接按比例缩会把两个节点叠在一起。实测它本质上是网格 ——
职业树严格 600×600，专精树以 600 为主，英雄子树 5×5 —— 所以按容差把坐标聚成
行列再摆格子。容差从 50 试到 250，同格重叠始终是 **0**，最大 9 列 × 11 行。

几件仍然做不到的事：

* **不能在面板里点着改天赋。** 现在是「看别人点的」，不是模拟器。
  （**读**官方天赋串这件事已经做到了，而且对着真值验过 —— 见下面「官方天赋串」一节。
  写一个编码器是没必要的：游戏自己就有导入 / 导出。）
* **上游有两个专精的数据是脏的。** WARRIOR/PROTECTION 的 77 套里有 1 套混进了
  战斗（Arms）树的节点，包括防战根本点不了的「掠夺者」系英雄天赋 —— 追到源头是
  **1 条玩家记录**被 WarcraftLogs 标错了专精。MONK/MISTWEAVER 有 4 套引用了一个
  raidbots 里不存在的 `entryID`。这两条都是上游的问题，`tools\verify-talent-tree.js`
  每次都会分开报出来（「跨专精污染」和「引用未知 entryID」），剩下 38/40 个专精干净。

### 官方天赋串：解开了，而且是拿真值验的

这一节记的是**调查结果 + 一个校验器**。`app\` 下的面板行为没变（它读的是预先解好的
天赋数据），但 `tools\decode-talent-string.js` 现在能把官方导入串解成节点表，
并且这件事**每次跑测试都会对着真值重新验一遍**。

这个解码器我前后做了十二轮，中间「验证」过五个错的假设。真正解开它的不是又一个猜测，
而是找到了**同一个生产者给出的正确解**：raider.io 的角色 profile 里，`talentLoadout`
既有导入串（`loadout_text`），又有它自己解出来的节点表（`loadout`，每项带
`node.id` / `rank` / `entryIndex` / `grantedNode`）。串和答案出自同一处，对不上就一定是我错了。

**结果：32 条串 × 2406 个节点真值，逐项全对。** 少解 0、`rank` 0 处不符、
`entryIndex` 0 处不符、`granted` 0 处不符。

```
node tools\verify-talent-decode.js   # 离线，只读仓库里的两份文件
node tools\fetch-talent-truth.js     # 重新抓真值（要联网）
```

真值落在 `tools\talent-truth.json`（38 KB，不含角色名和服务器），已提交，
所以克隆下来就能跑；`node tools\run-tests.js` 的第八行就是它。

#### 之前为什么一直解不开：是串的版本，不是布局

那个折磨了我五轮的「只有 7/54 干净」，根源是**串和天赋树不是同一版**。
同一批角色，两个来源的串放在一起量：

| 串的来源 | 语义干净 |
| --- | --- |
| raider.io 排行榜里的赛季历史串 | 3/32 |
| 同一批角色**当前**的 profile 串 | 27/32 |

「历史脏 → 当前干净」的有 **24 人**，反过来「历史干净 → 当前脏」**0 人**。
零反例。赛季历史串是照旧版天赋树编的，用今天的 `fullNodeOrder` 去读它，
从某个节点起就会整体错位 —— 那正是我一直看到的现象（第一个违规点的下标
在同一专精内恒定，因为那是**树改动的位置**，跟串的内容无关）。

本机存档那 54 个串也是同一回事：它们是我这几个月陆陆续续存下来的。

**布局本来就是对的。** 唯一真正错了的是两个默认值，都是拿真值发现的：

* `type='subtree'`（英雄天赋的选择节点）在 raidbots 里**没有 `maxRanks` 字段**，
  我拿它当兜底值，于是 `rank` 解成了 `undefined`。真值一致给 1 —— 英雄树只有
  「选了 / 没选」。改掉之后 `rank` 不符从 33 → **0**。
* 位流里**没有**「用了哪个 entry」这个字段。二选一节点带 2 位下标，
  其余多 entry 的节点（`type='tiered'`，界面上是同名三档）要按 `entries[].maxRanks`
  累加去推。改掉之后 `entryIndex` 不符从 25 → **0**。
  （**这一条的验证是不完整的**：32 份样本里 tiered 节点只出现过满级一种情况，
  所以「累加」和「永远取最后一档」给出同样答案，分不开。代码注释里注明了。）

还有一处不是错、但会让人以为是错的：**我会多解出一些节点**（32 条串共 37 个），
全都是 `granted`（系统白给的）。raider.io 的 `loadout` 数组**不列 granted 节点**，
这是它的口径，不是我的缺陷。校验器把这一项单独统计并打出来 —— 数字突然变 0 或者暴涨，
说明上游改了口径。

#### 顺带把节点顺序变成了仓库里的东西

解码要用的 `fullNodeOrder` 原来只在 `tools\.talent-raw\talents.json`（14 MB，
不进仓库）里，于是校验器在新克隆的仓库里跑不起来。现在它被写进了
`app\talent-tree.js` 的 `nodeOrder`（13 个职业共 2896 个 id，+18 KB）。

**按职业存一份，不是按专精存 40 份** —— 前提是「同职业各专精的顺序完全一致」，
这一条在生成时会**逐字校验**，不一致就直接拒绝生成（13/13 职业实测一致；
按专精存要 8970 个 id，3.1 倍）。

#### 串的格式（实测）

**节点顺序在 raidbots 那份 `talents.json` 里，字段叫 `fullNodeOrder`。**
它是**按职业**的，不是按专精 —— 同一个职业的每个专精拿到的 `fullNodeOrder` 完全相同，
而且正好等于该职业所有专精节点集合的并集。13 个职业全查了：

| 职业 | `fullNodeOrder` | 本专精的 | 别的专精的 | 对不上的 |
| --- | --- | --- | --- | --- |
| 死亡骑士 | 206 | 114 | 92 | 0 |
| 恶魔猎手 | 227 | 111 | 116 | 0 |
| 德鲁伊 | 282 | 120 | 160 | **2** |
| 圣骑士 | 233 | 126 | 106 | **1** |
| 其余 9 个职业 | 202~253 | 105~125 | 94~128 | 0 |

**`treeHash` 不在公开数据里** —— raidbots 每个专精只有 `classId / className / classNodes /
fullNodeOrder / heroNodes / specId / specName / specNodes / subTreeNodes / traitTreeId`，
没有 hash 字段。但它能从**你自己的存档**里挖出来：`WTF` 下的 `TalentLoadoutsEx.lua` 和
`BtWLoadouts.lua` 存的就是官方导入串。本机 36 个存档文件里找到 54 个串，
**54/54 都能解出合法的串头**：

```
8 位  序列化版本（全是 2）
16 位 specID
128 位 treeHash
```

字母表是标准 base64，每个字符内**低位在前**。
解出来的 `treeHash` 也是**按职业树**的：防护和惩戒圣骑士同一个 hash，
鲜血和邪恶死骑同一个，浩劫和复仇恶魔猎手同一个。

串头后面是按 `fullNodeOrder` 逐个节点的位流。这个布局能**原样再编码回去**：

```
1 位  选没选
  选了 → 1 位  是买的还是白给的
    买的 → 1 位 是否没点满，是则 6 位 点数
           1 位 是不是二选一，是则 2 位 选了哪个
```

**这里我先踩了一个自己的坑，值得写出来。** 我最初的验证方式是「往返比对」：解码再
编码、跟原串逐字符比，得到 28/54 一致，当时把它当成了「布局解对了」的证据。
它不是。往返比对在这里几乎测不出东西 —— 我是**读 n 位、再把同样的 n 位写回去**，
本质上是逐位抄一遍，字段含义猜错了照样一致。证据就在数字里：把点数位宽从 6 改成 4，
一致率只从 28 掉到 27。一个改了字段宽度还几乎不变的指标，测的不是字段。

真正能证伪布局的是**语义检查**，三条，都不依赖「点数上限应该是多少」这类猜测：

* 买下来的节点必须属于这个专精（`fullNodeOrder` 是职业级的，里面有别的专精的节点，
  但一套惩戒圣骑的配置不该买到防护的节点）
* 点数不能超过该节点的 `maxRanks`
* 只有真有两个 `entries` 的节点才能带「二选一下标」

按这三条重新量，本机存档那 54 个串里**只有 7 个干净**。我在这个数字上卡了五轮，
试遍了 18 种字段布局、四种节点顺序，最好的还是原来那个。
那五个被数据否掉的解释记在下面，因为它们的价值不在结论而在方法。

**真正解开它的不是又一个假设，是找到了判据。** raider.io 的角色 profile 里，
`talentLoadout` 同时给两样东西：`loadout_text`（导入串）和 `loadout`
（它自己解出的节点表，每项带 `node.id` / `rank` / `entryIndex` / `grantedNode`）。
**串和答案来自同一个生产者** —— 对不上就一定是我错了，没有第二种解释。
之前五轮我拿的都是**自我一致性**当证据（读 n 位写回 n 位、位数刚好用完），
而那种检查字段含义猜错了照样通过。

拿真值一比，布局**本来就是对的**，错的只有三处，而且都不是位流：

| 症状 | 真相 |
| --- | --- |
| 33 个节点 rank 解成 `undefined` | 英雄天赋的选择节点（`type=subtree`）在 raidbots 里**没有 `maxRanks` 字段**，我拿它当兜底就成了 `undefined`。真值一致给 1（英雄树只有「选了 / 没选」）。改成退到 1 后，rank 不符 33 → **0** |
| 25 个节点「二选一下标」对不上 | 那些是 `type=tiered`（界面上同名的三档），位流里**根本没有下标**，raider.io 是**从 rank 推**的：按 `entries[].maxRanks` 累加，落在哪一档就是那个下标 |
| 多解出 37 个节点 | 全是 `granted`（系统白给的）。串里确实有这些位，是 raider.io 的 `loadout` 数组**不列** granted 节点 —— 不是我多读了 |

改完之后：**32 条串 × 2406 个节点真值，少解 0、rank 0、entryIndex 0、granted 0，
32/32 逐项全对。** `granted` 就是 `purchased` 位的反面，这一条也是真值验的，不是推测。

那么原来的 7/54 是什么？**版本不匹配**，不是解码错误。同一批角色，
他们在排行榜里的**赛季历史串**干净 3/32，而**当前**的 profile 串干净 27/32；
「历史脏 → 当前干净」24 人，反过来 **0 人**。历史串是照几个月前的天赋树编的，
拿今天的 `fullNodeOrder` 去读当然错位。

这份判据已经钉进测试套件，不靠我下一轮还记得：

```
node tools\fetch-talent-truth.js     # 要联网，抓真值 → tools/talent-truth.json（38 KB，不含角色名）
node tools\verify-talent-decode.js   # 离线，只读提交进仓库的两份文件
node tools\mutate-decode.js          # 6 个变异，证明上面那条校验真的能失败
```

`verify-talent-decode.js` 是 `run-tests.js` 的第九行，克隆下来就能跑 ——
节点顺序表现在也提交在 `app/talent-tree.js` 里（`nodeOrder`，13 个职业 2896 个 id，
+18 KB），不再依赖那份 14 MB 的 gitignored 原始缓存。

**五个被否掉的解释**（留着是因为它们说明了「怎么算证据」）：

| 解释 | 怎么测的 | 结果 |
| --- | --- | --- |
| 字段顺序 / 宽度不对 | 18 种组合全试（额外位有无 × 位宽 4/5/6 × 顺序） | 干净的 **0** 个 |
| `partial`/`choice` 不该嵌套在 `purchased` 里 | `--flat` | **0/54**，还凭空造出 46 个超上限点数 |
| 节点顺序该只取本专精的 | 只留本专精节点 / 按 id 排序 | 都是 **0/54**，全量 `fullNodeOrder` 最好 |
| 跟主流 hash 不一致的串才失败 | 按 (专精, hash) 分组算干净率 | **事实相反**：一致的 5%，不一致的 42% |
| `fullNodeOrder` 只是比游戏的顺序差几个节点 | 按专精搜一组「幽灵节点」补丁，要求修好该专精**全部**串 | 补到 13 个仍然 **0/N**，10 个专精里只有 1 个不需要补丁 |

最后那一条当时看起来最有希望，两个线索都很强：**没有一个串是从第 0 个节点就错的**
（第一个违规点最早在整条顺序的 4% 处，中位 16%），而且**同一专精的不同串，
第一个违规点的下标完全相同**（复原萨满 8 个串都是第 35 个，复仇 DH 5 个串都是第 42 个），
连 `treeHash` 不同的也一样。按内容漂移会散开，下标恒定只能是顺序本身有系统性偏差 ——
这个推理没错，**偏差确实存在，就是版本差异**；错的是我以为能靠补几个节点补回来。
单条串靠**一个**补丁能修好（7 → 12），但同一专精的所有串**共用不了一组补丁**，
补到 13 个仍然 0/N。事后看，这正是「补丁越自由，吸收的误差越多」——
**「能修好一部分样本」从来不是假设成立的证据。**

至于 `treeHash`：**它不重要**。raider.io 公开给玩家粘进游戏的 99 个串，
`treeHash` **99/99 全是 0**。本机存档里也有 4 个全 0 的。
所以游戏根本不校验这 128 位。而且按用户的说法，**游戏自己就有导入导出**，
这个项目压根不需要编码器 —— 需要的只是把已经存在的串**读出来、解对**。

### 装备图标：图标是打包前下好的，离线可用

图标这件事绕了一圈，把结论和过程都记下来，免得以后重走。

**问题**：BisData 里 **2187 件装备一件都没有 `icon` 字段**（统计过，0 件），也没有
`quality`，只有 `itemId`。插件在游戏里能出图，是因为它调运行时的 `C_Item` 接口现查。

**试过但不行的路**：

* **游戏目录里的散装图标**。本机 `Interface/Icons` 下确实有 22786 个 `.blp`
  （全部 64×64 DXT5，我写了 `tools/blp.js` 能把它们解成 PNG，零依赖，验证过出真图）。
  但那是 2024-08 的旧提取：`inv_10* / inv_11* / inv_12*` 一个都没有，
  当前赛季的装备图标全不在里面。所以它当不了来源。
* **运行时去 wowhead 拉图**。国内**直连 403**（实测 `wow.zamimg.com`），指望用户那边能通不现实。

**现在的做法**：打包前把图标全下好，随发布包一起发。

```
node tools\fetch-icons.js
```

它做两件事，两个来源分工明确（都是本机 2026-08 实测的结论）：

| 要什么 | 从哪来 | 要代理吗 |
| --- | --- | --- |
| `itemId` → 图标名 + 品质 | `nether.wowhead.com/tooltip/item/<id>` | 要（直连 403） |
| 图标图片 | `render.worldofwarcraft.com`（暴雪自己的 CDN） | **不要，直连就通** |
| 暴雪 CDN 还没上的新图标 | `wow.zamimg.com` | 要 |

第三行是个意外：暴雪 CDN 有绝大多数图标，但**当前赛季**那批新图标它还没上传
（烈毒之渊的 `*_ulatek_d_01` 系列 158 个全 403，us / eu / tw / cn 四个区都一样），
只有 zamimg 有。所以下载是按源顺序试的，403 / 404 直接换源、不重试。

产物：`app/item-icons.js`（33.5 KB，`itemId → 图标名` + `itemId → 品质`）
和 `app/icons/` 下 462 个 56×56 的 jpg，约 1 MB。查询结果缓存在
`tools/.icon-cache.json`，中断后重跑只补没查到的。

**顺带纠正了一个我自己写错的地方**：我原先假设「BiS 列表里的东西都是紫装」，
把物品名硬编码成紫色。查出来的品质分布是 `{1: 14, 3: 54, 4: 500}` —— 附魔卷轴是蓝的、
合剂是白的。现在按查到的品质上色。

**消耗品用插件自带的图标名，不用 wowhead 的。** 插件那份是作者从游戏客户端抄的，
wowhead 对同一件东西可能给出后缀带 `-` 的变体名（`241324` 给 `..._white-`、
`241326` 给 `..._red--`，两张图在 zamimg 上都真实存在、md5 不同，都是合法的合剂图标）。
客户端那份更权威，就用它。

**设置里的「图标地址前缀」现在只是覆盖用的**：留空 = 用包里的 `app/icons/`，
填了才去别处取。想自己架图床的人可以用。

### 升级轨道（「英雄 6/6」）是解出来的，不是插件给的

BisData 每一行都带 `bonusIDs`（3963 行全部有），但那串数字在插件里**只有一个用途**：
拼游戏内的 `|Hitem:` 链接，让游戏自己的 tooltip 显示正确装等。网页没有这个机制，
装等本来也已经在行里了。所以原样存那 19 KB 是白花的。

有价值的是把它**解开**。AlterEgo 自带一张赛季轨道表（`Data/UpgradeTracks.lua`，
作者注明抄自 raidbots 的 `bonuses.json`），形如 `{name = "Hero", bonusIDs = {12841..12846}}`，
数组下标就是升级等级 1..6。拿它去撞 BisData 的 `bonusIDs`：

* **3601 / 3963 行（90.9%）能解出轨道**，剩下的多是旧赛季物品和套装坯子
* **没有任何一行同时命中两个轨道**（本机实测），所以不存在歧义
* 分布一眼就能看出当前赛季的形势：英雄 6/6 有 1685 行、英雄 3/6 有 1104 行

**为什么不能从装等直接推。** 实测有 3 个装等各对应两种轨道（308 / 318 / 321），
连 `(装等, 来源分类)` 都还有 5/24 组歧义 —— `321/团本` 是英雄 6/6 ×528 对 神话 2/6 ×10。
推不出来，只能存。存的是一个小整数（轨道下标 × 10 + 等级），比原样存 `bonusIDs` 省。

**轨道的中文名同样没有手写。** 两处**互相独立**的插件 zhCN locale 完全一致，
生成器两边都读，不一致就直接停：

```
EllesmereUILocales/zhCN.lua        L["Hero"] = "英雄"
ItemInfoOverlay/Locales/zhCN.lua   L["color.itemLevel.itemUpgrade.hero"] = "英雄"
```

五个名字都对上了：冒险者 / 老兵 / 勇士 / 英雄 / 神话。
（`ItemInfoOverlay/Utils.lua` 的代码注释里把 Myth 写成「史诗」，但那是注释不是 locale，
两个 locale 都写「神话」，所以按 locale。）

**这套解码用第三方数据独立验证过。** raidbots 的 `bonuses.json`（1.7 MB，本机直连可取）
里每个升级 bonusID 都带 `upgrade.fullName`，例如 `12846 → "Hero 6/6"`。拿它对一遍：

| 对比项 | 结果 |
| --- | --- |
| 赛季 18 的 30 个 bonusID：轨道名 + 等级 + 满级 | **30 / 30 完全一致** |
| BisData 实际用到的 12 个 bonusID：装等 | **12 / 12 完全一致** |
| 解不出轨道的那 37 个 bonusID | 确认**本来就不是轨道** —— 是插槽、制造属性、附加效果、服务器端标记 |

换句话说，「解不出轨道」的那 362 行不是漏了，是那些行真的没有轨道信息。

### 换赛季 / 数据更新了怎么办

两条路：

**本地重新生成**（插件更新过之后）：

```
node tools\gen-bis.js
node tools\gen-talents.js
node tools\fetch-icons.js
node tools\fetch-talent-tree.js
node tools\fetch-class-names.js
node tools\fetch-talent-truth.js
```

**后四步都不能省，而且都要联网。**

`fetch-icons.js`：换赛季会进来一批新 itemId，`app/item-icons.js` 里没有它们，
面板就会把新装备画成占位块。它只补缺的（查询结果缓存在
`tools/.icon-cache.json`），所以重跑很快。图标名走代理查
wowhead，图片从暴雪 CDN 直连下，当前赛季那批新图标 CDN 上还没有、会自动退到
zamimg（走代理）。

`fetch-talent-tree.js`：新赛季会改天赋树（挪节点、加删天赋）。不重跑的话，
新出现的 `entryID` 在树里找不到，那些天赋就不会高亮。它从 raidbots +
wago.tools 直连取数据（**不用代理**），原始文件缓存在 `tools/.talent-raw/`（14 MB，
不进版本库也不进发布包），中文名的连接结果缓存在 `tools/.talent-names.json`。
有缓存的话加 `--offline` 可以完全离线重新生成。

`fetch-class-names.js`：加了新专精就得重跑（11.0 就加了恶魔猎手的**噬灭**，specID 1480）。
不重跑的话新专精在 `app/class-names.js` 里查不到中文名，只能显英文 token。
两张 DB2 表加起来 15 KB，很快。

`fetch-talent-truth.js`：**跟着 `fetch-talent-tree.js` 一起重跑。**
天赋串解码的真值（`tools/talent-truth.json`）是照某一版天赋树抓的，树换版之后旧真值
会把「版本漂移」误报成「解码错」—— 这不是假设，正是它把我坑了五轮：同一批角色的
赛季历史串干净 3/32，当前串干净 27/32。校验器会显式提醒版本不一致，
但提醒不如重抓。它抓的是 raider.io 当前排行榜前列玩家的 profile，一次几十条。

跑完 `node tools\run-tests.js`，渲染检查、无障碍检查和三个数据校验会告诉你有没有漏 ——
其中「40 个专精全是中文名」那一条就是专门拦这个的：漏跑了它会直接红。

默认读 `E:\World of Warcraft\_retail_\Interface\AddOns\` 下的插件，
路径不一样用 `--lua <路径>` 指定。生成器复用 `app/lua-parser.js`（项目自己那个有测试的解析器），
并且**会自检**：装备池去重时如果发现「本该静态的字段」不一致就直接退出，
天赋差异编码会当场还原一遍比对，还原不上就报错。第一版就是靠这个自检抓到
`source` / `bossName` 不是静态字段（166 处冲突）。

**远端覆盖**（设置 → 其他 → 数据源，填一个地址）：填了之后面板会先试
`<地址>/bis-data.js`、`<地址>/talent-data.js`、`<地址>/talent-tree.js`、
`<地址>/item-icons.js`，取不到再退回包里那份。文件必须是**赋值到全局变量的 js**
（`window.AE_BIS = {...}`），不能是 JSON —— `file://` 下 `fetch()` 不可用，
`<script src>` 是唯一能跑的加载方式，这一点 `index.html` 顶部已经记着了。

### 换数据源：面板只认格式，不认来源

装备数据现在来自 GearInsight，但它有几个说不清的地方（见下面「数据质量」）。
将来可能换成别的来源，所以中间那层格式是有定义的、且机器能验：

```
node tools\verify-bis-data.js
node tools\verify-bis-data.js --data path\to\bis-data.js
```

`tools/verify-bis-data.js` **本身就是那份格式说明** —— 顶部的 `SCHEMA` /
`SPEC_SCHEMA` / 行格式注释是可执行的文档，不会像另写一份 .md 那样跟代码脱节。
2016 项检查，涵盖字段在不在、类型对不对、下标越不越界、可选位有没有跳着省。
**换来源时只需要换生成器**：新生成器的输出能过这个校验，面板就能直接用。

它和 `app/bis-tests.js` 的分工是有意分开的：这里管**格式**（换数据源时最容易踩的坑），
`bis-tests.js` 管**内容合理性**（40 个专精、使用率不超 100、图标覆盖率）。两边有重叠，
重叠处坏了会被抓两次，比漏掉好。`node tools\run-tests.js` 会把两样都跑掉。

天赋树是同一个套路，另一个校验器：

```
node tools\verify-talent-tree.js
node tools\verify-talent-tree.js --tree path\to\talent-tree.js
```

76377 项检查。除了格式，它还**顺带交叉验证 `app/talent-data.js`** —— 把每套天赋的
`entryID` 拿到树里查，分两种情况报：`entryID` 在树里但属于**别的专精**（上游标错专精），
和 `entryID` 在 raidbots 里**根本不存在**。这就是上面那两条上游脏数据被发现的方式。

第三个校验器管的不是数据格式，而是**我的解码器对不对**：

```
node tools\verify-talent-decode.js
```

它离线跑，只读两份提交进仓库的文件（`tools/talent-truth.json` + `app/talent-tree.js`），
拿 32 条真值串 × 2406 个节点逐项比 `rank` / `entryIndex` / `granted`。
为什么单独列一条：这个解码器我前后做了十一轮，反复「验证」过五个错的假设，
每次都是拿**自我一致性**当证据。真正把它解开的是拿到了**同一个生产者给出的正确解**，
详见上面「官方天赋串」一节。

这三个校验器都是**变异测试过的**：往数据里注入 30 处 / 31 处坏值，必须每一处都报错；
解码器那份注入 6 处（改位宽、去掉 `granted` 取反、拆掉 `entryIndex` 推导、
把真值文件截成 1 条），也必须每一处都报错。
渲染断言也一样 —— 故意让面板「不画名字」「不画连线」「把专精树画成职业树」，
`run-tests.js` 必须失败。没被变异测试过的测试，等于没测过。

**变异套件之间是互斥的**，因为它们真的在磁盘上改源文件。这一条不靠记性：
`tools/mutate-lock.js` 是一把锁，变异工具开跑时占、退出时放，`run-tests.js`
发现锁就拒绝跑并说明「这是竞争，不是缺陷」。加它的起因是我把套件和三个变异脚本
塞进同一个并行块，结果套件报「7947 个 `<img>` 没有 `alt`」，同一次输出里
`mutate-a11y` 又是 5/5 通过 —— 两个结论互斥，真相是它读到了被变异改坏的中间态。

### 无障碍：先修尺子，再看读数

`run-tests.js` 第六行是无障碍检查，四条硬断言：每个 `<img>` 都要有 `alt` 属性、
每个 `<button>` 都要有可读的名字、每个带 tooltip 的元素**自己**要有可见文字
（tooltip 是补充说明，不是元素的名字），以及天赋树的画布要有 `role="group"`
和一句中文说明（鲜血死骑实际生成的三句：「职业天赋，共 44 个天赋，点了 31 个，合计 35 点」
「专精天赋，共 41 个天赋，点了 30 个，合计 34 点」「英雄天赋：萨莱因，共 14 个天赋，点了 14 个，合计 14 点」）。

这一节值得写下来的其实是**过程**，因为我第一次量出来的数字全是错的。
第一次跑出来是「621 个图标全都没有 `alt`」，看着像个大 bug。实际上代码写的是
`img.alt = ''` —— **属性赋值**，浏览器会反射到 attribute 上，而我的测试桩不反射，
于是 `attrs.alt` 是空的。缺陷不在面板里，在尺子上。
给桩补上 `alt / title / src / id / value / width / height` 等的属性反射之后再量：
**图标 7947/7947 都有 `alt`，按钮 2859/2859 都有名字，带 tooltip 的元素 26378/26378
都有可见文字**。装备图标旁边就是装备中文名，所以 `alt=""`（有属性、值为空）是对的写法 ——
缺属性才是问题，那会让读屏软件去念文件名。

真正查出来的缺陷只有一个：**天赋树的 129 个画布都是没有名字的 `<div>`**。
那是一堆绝对定位的方块拼出来的图，读屏软件念到的是一串互不相干的天赋名，
读不出「这是一棵树、点了多少点」。加了 `role="group"` + 中文说明。

这四条断言也变异测试过，5 个变异全被抓到（包括两个「把可见文字删掉、只留 tooltip」
的变异 —— 那正是这组断言存在的理由）。这一套变异落在 `tools/mutate-a11y.js`，
是**长期文件**，不是用完就删的临时脚本 —— 前面三套变异套件都叫 `_*.js`，
结果被清理命令一并删了，断言还在但「能证明断言有效」的东西没了，每改一次就要重写一遍。
它和 `run-tests.js` 一样不进发布包（`build-release.ps1` 的 `$dropFromPkg` 里排除了）。
跑法：`node tools\mutate-a11y.js`，它会自己报「锚点失效」，因为一个没打上的变异
会假装成「断言很强」—— 实测踩过一次。顺带说明一句：完整的无障碍验证需要用读屏软件
实际测试并由专业人士评审，命令行断言只能覆盖能自动检查的那部分。

**变异套件之间、以及和测试套件之间不能并行跑。** 变异测试是**真的在磁盘上改源文件**
再跑一遍套件、改完还原，所以两个进程同时开就会互相污染。我踩过：把
`run-tests.js` 和三个变异脚本放进同一个并行块，套件读到的是被变异工具删掉
`img.alt = ''` 之后的 `app/bis.js`，于是报「7947 个 `<img>` 没有 `alt`」，
而同一次输出里 `mutate-a11y` 又是 5/5 通过 —— 两个结论互斥，真相是竞争，
源文件其实好着的。查了一轮才确认。

靠记性记住「别并行跑」不够（这个项目里靠记性的规矩已经失手四次），所以有
`tools/mutate-lock.js`：变异工具开跑时占锁、退出时释放，套件发现锁就直接拒绝跑并
说清「这时候的读数全都不可信」。锁本身也验过能双向失败：手动占锁后套件退出码 1，
第二个变异工具也退出码 1，释放后两边都恢复正常。

还有一条守卫是给**发布包**的：`tools/` 是被整个目录递归复制进 zip 的，
`.gitignore` 管不到它，所以每个测试专用脚本都必须写进 `build-release.ps1` 的
`$dropFromPkg`，每个上游缓存目录必须写进 `$dropDirsFromPkg`。这一条也是一项检查
（`run-tests.js` 最后一行），判据两条：引用了测试脚手架，或者文件名是 `mutate-*.js`。
第二条是后补的 —— `mutate-decode.js` 跑的是校验器、一个字都没提脚手架，
于是第一条漏掉了它，守卫报「4 个」而实际有 5 个。补上之后它连着抓到了
`mutate-lock.js` 和 `mutate-pkg.js` 两个新文件，都是我没主动去加的。
这个守卫自己也变异测试过：`node tools\mutate-pkg.js`，**4/4**
（名单里删一个脚本 / 把脚手架名拼错 / 缓存目录名单里删一个 / 把目录名拼错）。

### 职业 / 专精中文名：病根是「按英文名建表」

现在 **13 个职业 + 40 个专精全部是中文**，来源是暴雪自己的 DB2 表
（`ChrClasses` / `ChrSpecialization`，wago.tools 导出，`locale=zhCN`），
落在 `app/class-names.js`（2.2 KB，`tools/fetch-class-names.js` 生成）。

值得写下来的是之前错在哪里。GearInsight 的 `specRawToCN` 是**只按专精英文名**建表的，
而专精英文名**不唯一**：

* `FROST` 一个键对两个专精，死骑的冰霜继承了法师的名字，显示成「**冰法**」——
  中文客户端里死骑不可能叫冰法，那是别的职业的专精名；
* `PRESERVATION`（唤魔师）和 `DISCIPLINE`（牧师）**根本没有行**，只能显英文。

所以修法不是「把三个名字补上」，而是**换成按 `specID` 建键**——
`specID` 是唯一的，死骑冰霜是 251，法师冰霜是 64，根本碰不到一起。
换完之后：251 → 「冰霜」、256 → 「戒律」、1468 → 「恩护」，
还白括了一个之前根本没名字的新专精：1480 → 「噬灭」。
缺的那 4 个职业名（唤魔师 / 法师 / 武僧 / 潜行者）也一并齐了。

没有一个名字是我打的。生成器里有四条**硬校验**，不过就拒绝生成：

1. 「玩家职业」得恰好是 13 个。这一条用**两条互不相关的定义**各算一次并要求结果相同：
   「专精数 ≥ 3」和「被天赋树的 40 个专精覆盖到」。
   （第一版只写了「有专精的职业」，结果数出 14 个 —— DB2 里有个 `ClassID 14`
   「冒险者」带着一个专精，它不是玩家职业。硬校验当时就拦下来了。）
2. 每个名字都得含中文字符。
3. **两个独立的暴雪来源必须逐字一致**：之前内置的 9 个职业名是从你自己
   SavedVariables 里角色自带的 `class.name` 抄的，DB2 那份是另一条路。
   它们实测 **9/9 逐字相同**。不一致就硬失败 —— 那时候「显示的是中文」反而更危险。
4. `app/talent-tree.js` 的 40 个专精必须全部查得到中文名。

解析顺序是「你的设置 > DB2 > 内置表 > 插件自带 > 英文 token」。
DB2 那一档也过 `hasCJK`：万一哪天下到的是英文表，它会被跳过，而不是让英文顶上去。

这一组断言也变异测试过（`node tools\mutate-names.js`，**5/5 全抓**），
其中一个变异是「把 `app/class-names.js` 整个藏起来」—— 因为那正是最阴的失败模式：
缺了它会静默退回旧兜底表（4 个职业显英文、死骑冰霜显 `FROST`），
而旧的那些断言只要求「非空」，英文也能过。现在 `run-tests.js` 把它当**硬依赖**，缺文件直接报错。

重新取数（换赛季、出了新专精时）：

```
node tools\fetch-class-names.js
node tools\fetch-class-names.js --refresh   # 强制重下两张 DB2 表
```

## 三件需要先知道的事

**1. 数据是稀疏的，这不是 bug。**
AlterEgo 只在你**实际登录某个角色**时才抓它的宝库 / 货币 / 藏宝图，而且周重置时会清空。
所以小号大多是空的。要让某个角色有数据，本周重置后登录它一次。

**2. 数据只在退出游戏 / reload UI 时才写盘。**
页面显示的是「上次登出时的状态」。每个数据源都标了最后写入时间，超过 14 天会打警告。

**3. 战网账号名在磁盘上无法还原。**
`Config.wtf`、`config-cache.wtf`、`cache.md5`、`Launcher.db`、`.product.db` 全查过，
没有邮箱也没有可读名字，只有 `L123456789` 这样的文件夹名。在设置里给它起别名即可。
（`#3` / `#4` 后缀能看出两个属于同一个战网账号。）

## 扫描失败了怎么办

扫不到数据的原因不止一种，修法也完全不一样，所以 `scan.ps1` 会先判断是哪一种，
再让启动器用中文说清楚下一步做什么。判断结果以 `SCAN_ERROR=<码>` 的形式打在扫描输出里：

| 码 | 情况 | 怎么修 |
| --- | --- | --- |
| `NO_WOW` | 没找到游戏安装目录 | 用对话框上的「设置游戏目录」，或手改 `tools/config.json` |
| `NO_ADDON` | `Interface\AddOns` 下没有 AlterEgo | 装插件，然后进游戏 `/reload` 一次 |
| `ADDON_BROKEN` | 有 AlterEgo 文件夹但没有 `AlterEgo.toc` | 解压多套了一层，把里层挪出来 |
| `ADDON_DISABLED` | 所有角色都把 AlterEgo 关了 | 角色选择界面的「插件」里勾上 |
| `NO_CHARACTER` | 这个目录里没有任何角色数据 | 目录选错了，或者从没登录过 |
| `NO_SAVEDVARS` | 插件装好也开着，但还没存过盘 | 登录角色，再 `/reload` 或退出游戏 |
| `SV_UNREADABLE` | 找到 `AlterEgo.lua` 但读到的是半截 | 完全退出游戏后重试；还不行就是文件坏了 |

最后一条最容易误解：**插件的数据只在 `/reload`、退出登录、退出游戏时才写盘**，
游戏开着的时候它只在内存里。所以「装了插件但看板是空的」几乎总是没退出过游戏。

`ADDON_DISABLED` 是逐角色判断的 —— 读 `WTF\Account\<账号>\<服务器>\<角色>\AddOns.txt`
里的 `AlterEgo: enabled` / `disabled`，全部角色都是 disabled 才报这个。

对话框里的「详细信息」是扫描器的原始输出（英文，因为控制台是 936 代码页），
「复制详情」可以直接粘给作者。

## 找不到游戏目录怎么办

自动探测顺序：`tools/config.json` → 从本文件夹往上找 → 注册表 → Battle.net 配置 → 常见位置浅扫。

都失败时编辑 `tools/config.json`，**反斜杠要写两个**：

```json
{ "wowPaths": ["E:\\World of Warcraft"] }
```

其他可选项：`excludeAccounts` 跳过某个账号，`accountAliases` 起别名，
`historyWeeksToKeep` 保留几周快照（默认 12，每周大约等于你几份 AlterEgo.lua 的总大小），
`absorbDownloadedSettings` 是否从下载文件夹回收设置。

## 设置怎么带走

浏览器的本地存储在 `file://` 下是**所有本地页面共用一个桶**，既不随文件夹走，
也可能被别的本地网页覆盖。所以：

* 日常改动存在浏览器里，即时生效
* 想带走：设置 → 「保存设置到文件」→ 下次运行 `启动.bat` 时自动从下载文件夹收进 `data/settings.js`
* `data/settings.js` 随文件夹走，换机器时按时间戳自动取较新的那份

### 移动或改名文件夹以后，设置好像被清空了

没被清空，是被**按路径分开存**了。所有本地页面虽然共用一个桶，但这个工具在桶里
用的键带了一段文件夹路径的哈希 —— 不这么做，同一台机器上放两份就会互相覆盖。
代价是路径一变（移动、改名、U 盘盘符变了、复制成第二份），键就跟着变，
原来那份设置还在桶里，只是当前这份看不见它了。

现在有两条路把它找回来：

* **自动**：新位置**还没有**自己的设置时，打开看板会自动把桶里最新的那份搬过来，
  并弹一次提示说明发生了什么。
* **手动**：新位置**已经**用过、已经有自己的设置了，自动迁移就不会动手
  （悄悄覆盖你正在用的设置比原问题更糟）。这时去
  **设置 → 其他 → 旧路径的设置**，那里会按时间列出桶里其他路径的设置，
  点「取回」即可。取回**不会**销毁来源，取错了还能再取回来。

要彻底摆脱这个问题，用「保存设置到文件」把设置写进 `data/settings.js`，
它是随文件夹走的。

## 实现上几个刻意的选择

**PowerShell 不解析 Lua。** 它只负责找文件、读字节、用 `ConvertTo-Json` 转义。
解析和渲染全在浏览器 JS 里：JS 写 tokenizer 更好写好测，`data.js` 保留原始 Lua
所以以后加字段不用重跑扫描器，而且同一个解析器直接复用于历史快照。

**错误分类在 PowerShell 里，中文文案在 C# 里。** 扫描器的控制台输出必须是纯 ASCII
（代码页 936），所以它只输出 `SCAN_ERROR=<码>` 和几行 `SCAN_DATA=<键>=<值>`，
由启动器翻成中文的原因 + 步骤 + 对应按钮。这样判断逻辑（哪种失败）和表达（怎么说）
各在它该在的地方，加一种情况只要加一个码和一段文案，不用动另一边。
从前是把扫描器的英文日志整段塞进 MessageBox —— 对着用户念日志不算提示。

**专业只能来自别的插件。** AlterEgo 的存档里没有专业字段，所以「专业」这一组列是
BagSync 喂的，靠 `guid` join。这是刻意做成可选增强而不是硬依赖：没装 BagSync 时那一组
列根本不生成，其余功能一个不少 —— 它首先是 AlterEgo 的看板。取「当前资料片的等级」
用的是「带等级的分类里 ID 最大的那个」，`orderIndex` 和「把所有分类都当技能线」两个
更直觉的规则实测都会出错，详见「专业列」一节。

**列身份永远是游戏 ID，不是数组下标。** `mythicplus.dungeons` 是位置数组，
实测存档顺序 `250,584,587,588,399,586,585,249` 和插件自己的定义顺序完全不同
（Lua 哈希迭代产物）。按下标取会让每个副本的分数静默落到错误的列里。
`tests.html` 里有专门的回归测试守这一条。

**解析器必须深度感知。** `name` 在 `info.name` / `info.race.name` / `info.class.name` /
`savedInstances[].name` 都出现；`level` 同时是角色等级、装等浮点、钥石层数和团本难度 ID。
扁平 regex 一定抓错。另外存档**零缩进**（一万多行全部顶格），按行判断嵌套也不行。

**中文名全部是从游戏数据里还原的，不是手写的。** 存档里没有「副本名称」这个字段，但中文名
藏在别的地方，有两个独立来源：

* **副本锁定记录** `raids.savedInstances[].name` 是已本地化的，且
  `Data.dungeons[].mapId` 正好等于 `savedInstances[].instanceID`
* **钥石的物品名** `|Hkeystone:180653:399:11:...|h[钥石：红玉新生法池 (11)]|h|r` ——
  链接里第二个字段就是 `challengeModeID`，方括号里就是中文名

一开始我手写过一张中文表，`塞塔里斯神庙` 被我写成了 `塞泰里斯神庙` —— 从游戏字符串里读
就没有这类错误。学到的名字会缓存，锁定和钥石都过期之后仍然记得。

**但只靠还原是不够的，这是 v1.13.2 修的 bug。** 还原出来的名字只在「当前有锁定或者包里有
钥石」的时候存在。周重置之后两样都没有了，唯一挡在你和一整行英文表头之间的就是那份缓存 ——
而缓存在 localStorage 里，按文件夹路径分桶、所有 `file://` 页面共用一个桶、文件夹一改名就
换桶。团本更糟：**团本压根没有缓存**，所以团本表头每周都会变回英文。

所以现在是三层：**游戏数据还原 → `app/labels.js` 里的内置中文表 → 英文**。内置表里每一个
名字都是从本机存档里抄出来的游戏字符串，不是我的翻译（这条规则就是上面那个错别字换来的，
没亲眼见过客户端输出的名字不要往里加）。团本也补上了自己的缓存 `learnedRaidNames`。

缓存是设置里的一段普通 JSON，用户能手改，而它的优先级高于内置表 —— 所以合并的时候只收
「键是数字、值是含中文的字符串」的行，否则一个脏值会被 `String()` 成 `[object Object]` 直接
变成表头。

表头的两字缩写（毒牙 / 密谋 / 纳洛…）从中文名自动截取，撞名会自动加长到三四个字，四个字
还撞就在后面加序号（毒牙2）——**不再退回英文缩写**。两个一样的表头比一个英文表头更糟，但
加了序号的中文表头两者都不是。团本表头同理（虚影普 / 潮缚英）。

**赛季中文名也是抠出来的。** 插件的 `Seasons.lua` 只有英文（`Midnight - Season 2`），但宝库
的要求文案 `击败%d个至暗之夜第2赛季首领` 里带着中文赛季名：去掉 `击败%d个` 前缀和 `首领`
后缀就是 `至暗之夜第2赛季`，再配上 `seasonDisplayID` 得到 `S2`。

**表头列组的 colSpan 必须跟着可见列数变。** 隐藏一列时 `display:none` 会让单元格从行里
彻底消失，如果分组表头的 colSpan 还是原来的数字，它右边所有分组都会整体偏移一格 ——
症状就是「宝库的数据跑到大秘境下面」。

**Excel 导出是手写的 zip。** xlsx 就是一个装着 XML 的 zip，而 zip 允许「存储」（不压缩）
条目，所以只要自己算 CRC32 就能生成合法文件，不需要任何库 —— 这才符合「整个文件夹拷走就能用」。
两个容易踩的点：`CT_Worksheet` 的**元素顺序是 schema 的一部分**
（`sheetViews` → `cols` → `sheetData` → `autoFilter`，顺序错了 Excel 直接报文件损坏）；
数字要写成数值单元格而不是文本，否则导出的表格没法排序和画图。

**护甲类型按职业推导。** 存档里没有这个字段，但 `equipment[].itemSubType` 有本地化的
「板甲 / 锁甲 / 皮甲 / 布甲」。职业映射更可靠（没有装备记录的角色也能算），装备只用来交叉
校验并在鼠标提示里说明。

**宝库 type 是用真实数据定死的**：`1` 大秘境（阈值 1/4/8）、`3` 团队副本（2/4/6）、
`6` 地下堡（2/4/8）。另外 `slots[].raidString` 在**每一行**都是团本文案
（「击败 N 个…首领」），直接拿来用会让大秘境和地下堡档位显示错误的要求，
所以只有团本行用它。

**宝库不显示示例奖励。** 存档里有 `slots[].exampleRewardLink`，但它不进界面。两个原因：
它来自 `C_WeeklyRewards`，每种活动**只返回一件**，不是每档一件 —— 实测同一个角色三个团本
档位存的是同一个 item ID（本机数据里 `item:270175` 在三行里逐字节相同），所以每档打印一次
会看起来像「三档会掉三件不同的装备」；而且它只是暴雪拿来预览装等的样例，不是承诺，
对「这周该刷哪个角色」这个问题没有任何帮助。装等的目标由钥石层数那一列给出（`+10 → 318
装等`），那是查表得来的确定值。

解析仍然保留（`AE.parseItemLink` 有自己的测试），因为字段本身没坏，只是不该占宝库格子的
位置 —— 以后要用随时能取。

**「本周完成」只显示大秘境本数。** 存档里 `numCompletedDungeonRuns` 有三个数（大秘境 /
史诗 / 英雄），原来格子里写成 `7 / 0 / 0`。后两个是**非钥石**难度，回答的是另一个问题，
而且实测本机 16 个角色里史诗只有 1 次、英雄 0 次 —— 两个几乎恒为 0 的数字占掉了和真正有用
那个数一样多的宽度。现在格子里只有大秘境本数，三个数和合计都在鼠标提示里。

排序跟着改成按**格子里显示的那个数**排，不再按合计。否则 `大秘境 4 / 史诗 1` 会排在
`大秘境 4 / 史诗 0` 前面，而两格看起来都是 `4`，像 bug。导出的那一列同样改成大秘境本数：
导出跟界面对不上是更难发现的坑。

**鼠标提示是自己画的，不用原生 `title`。** 原生提示对一张要横扫的宽表来说不可用：要悬停
约 1 秒才出现（快速划过什么都看不到）、约 5 秒后自己消失（4 行的宝库格子读一半就没了）、
而且消失之后**指针只要还在同一个格子里就不会再出现**，必须移出去再移回来 —— 这正是
「不是每次指向都有显示」的原因；此外底下 DOM 一重建它就无声地消失。

所以文案仍然照旧写在各处的 `title` 属性里（31 处，加上抽屉），`app/tip.js` 在第一次悬停时把它
搬到 `data-tip` 并删掉 `title`（删掉才是关键，否则两个气泡一起出现），同时写进 `aria-label`
让读屏软件还能读到。事件委托在 `document` 上，因此每次 `AE.rebuild()` 之后不需要重新绑定。
延迟 90 ms：足够短像是即时响应，又不会让指针扫过二十列时每格闪一个提示。

**周快照按 `weeklyReset` 纪元值分桶，不用 ISO 周。**
ISO 周从周一算起，WoW 周重置不是，混用会把一个游戏周劈成两份、把两个并成一份，
每个周增量都算错。

**必须是经典 `<script>` 标签。** `file://` 下 ES 模块、`fetch`、XHR、Worker 全部被拦。
`index.html` 顶部有注释说明，别改成 `type="module"`，会立刻整页报 CORS 死掉。
`<meta charset="utf-8">` 也必须是 `<head>` 第一个元素，否则 Chromium 会按系统
locale 回退到 GBK，所有中文乱码。

**纹章的上限不是「持有 / 上限」，所以格子里是「现有(已获取/上限)」。** 纹章的
`useTotalEarnedForMaxQty = true`，意思是上限卡的是**累计获得量**，不是当前持有量。实测数据：
冒险者迷雾纹章 `quantity=575, totalEarned=205, maxQuantity=300`。写成「575/300」看着就像 bug；
回答「还能拿多少」的数字是 `205/300`，还差 95。

但只显示 `205/300` 又把**你实际能花的那个数**藏起来了 —— 575 个就躺在包里。所以现在两个都给：
`575(205/300)`，粗体是现有，括号里是已获取 / 上限。只在两者**不相等**时才这么写；相等的时候
（`潮汐火花尘 5/5`，持有量本身就是受限的那个数）仍然是 `5/5`，写成 `5(5/5)` 只是噪音。
没有上限的货币（比如额外奖励货币）就只显示持有量。

列宽因此从 78 提到 96：最宽的真实内容 `575(205/300)` 要 67px，78 的列只有 66px 可用，会被裁成
省略号 —— 而一个被裁掉的数字读起来是**错的数字**，不是「窄了一点」。

**货币表头缩写有一张按 currencyID 的覆盖表。** 通用规则是去掉共有的类别后缀
（`冒险者迷雾纹章 → 冒险者迷雾`），因为区分度全在前缀。但有几个规则搞不定，走
`L.currencyShortZh`：`修复的宝匣钥匙 → 钥匙`、`宝匣钥匙碎片 → 钥匙碎片`、
`未被污染的法力水晶 → 法力水晶`、`晦暗虚空核心 → R币`。

**键必须是 currencyID 而不是名字**：3418 和 3513 是两个不同赛季的不同货币，游戏给的名字
**一模一样**都叫晦暗虚空核心，按名字建表就没法区分。（两个都映射到 R币 是故意的 —— 它们是
同一样东西的两个赛季版本，而且非当前赛季那列默认就是隐藏的。）

顺带修掉一个 bug：原来在去后缀之后还有一条**去前缀**规则（迷雾 / 曙光 / 晦暗 …）。实测它触发
3 次、0 次产生有用结果 —— 每次都把前一步的结果整个吃光，变成空字符串，然后 `|| name` 退回
**全名**。这就是 `光耀火花尘`、`晦暗虚空核心`、`黎明之光法力熔剂` 三个表头一直没被缩短的原因。

还有一条通用的「去掉 `的`」规则被我否掉了：`^(.{2}).*的(.{2})$` 能把 `守护巨龙的酣梦纹章` 变成
`守护酣梦`，但它会命中任何**带 `的`** 的名字 —— 测试里 `某种没见过的货币` 直接被缩成 `某种货币`。
宁可给那两个多写一行覆盖，也不要一条会误伤未来货币的规则。

**上限是 5 个字，正好 5 字的不动。** `冒险者迷雾`、`风化安德麦`、`雏龙的酣梦` 这些停在 5 字，
没有为了整齐再砍一刀 —— 同一族里 `守护酣梦` 是 4 字（它的全名 9 字，不砍不行），看起来不齐，
但把 `安德麦` 砍成 `安德` 只会更难认。`苏生奇梦` / `苏生觉醒` 保留全名：后缀规则里原本有
`奇梦|觉醒`，而全游戏只有这两个货币以它们结尾，剥掉的结果是两个表头都变成 `苏生`，
**两个一样的表头比一个长表头更糟**。从正则里删掉这两条就等于保留全名，不需要写覆盖。

`藏宝图 持有 / 本周 / 在身` 三列的表头是 `宝图 X`：它们本来就在「地下堡 / 藏宝图」这个分组带
下面，前缀是冗余的。这三个不是货币，改的是 `columns.js` 里的 `label` 字面量，不走覆盖表。

守门测试 `表头没有一个超过 5 个字` 按 **CJK 字宽**（ASCII 空格算 1/3 个汉字，所以 `宝图 持有`
是 4.5 字）检查 `buildColumns()` 出来的**每一个**列，不只是货币列。新赛季塞进来一个长名字会在
这里失败，而不是悄悄把表撑宽。

**外部主页链接：一个实测过，一个没有。** Raider.IO 已验证——
拿一个中文服务器名的真实角色试过，`https://raider.io/characters/cn/<中文服务器>/<角色名>`
返回 200，中文服务器名和英文 slug 都能用，
所以直接用存档里的中文名，不需要额外查表。Warcraft Logs 对任何脚本请求都返回 403
（连故意写错的角色名也是 403），**它的链接格式没能在本机验证**，用的是文档里的
`/character/<region>/<realm>/<name>`。两个前缀和服务器名形式都做成了设置项，点开发现不对可以自己改。
`CN史诗地下城` 这类跨服分区不是真服务器名，那几行不会生成链接。

**更新检查在 PowerShell 里做，不在网页里。** `file://` 下 `fetch` 和 XHR 被完全禁掉，网页
根本没有联网能力。所以 `scan.ps1` 调 GitHub Releases API，把结果写进 `data.js`，网页只负责显示。
只访问 `api.github.com`，不发送任何本机信息；在 `tools/config.json` 里把 `checkForUpdates`
设为 false 就完全不联网。

**检查失败时什么都不显示。** 国内网络访问 api.github.com 经常超时，每次启动都提示
「无法检查更新」是噪音不是信息。所以只有确实拿到了更新版本号才出横幅，其余情况只在标题栏
显示当前版本号（鼠标悬停能看到失败原因）。

**但托盘菜单里手动点的「检查更新」是另一回事，必须有反应。** 那是用户主动问的问题，
静默就是耍赖。它现在会：立刻弹一个「正在联网检查更新...」的小窗（不再是点完几十秒没动静），
直接发一个 HTTPS 请求问 GitHub（约 0.5 秒，不再顺带重扫整个游戏目录），
然后用**对话框**给结果——有新版本就问要不要打开发布页，已是最新就直说，
失败就解释多半是网络问题并给个手动入口。

早先这里用的是气球提示（BalloonTip），这是个错误：Windows 10/11 把它转成通知，
而通知常常被专注助手或通知设置整个吞掉。加上当时要先跑完一次全量扫描才出结果，
两件事叠起来，用户看到的就是「点了完全没反应」。

**导出提示只能做到这一步。** `file://` 页面下载的文件落在浏览器的下载目录，而网页既不能
导航到 `file://`，也没有「在文件夹中显示」这种 API。所以 `scan.ps1` 顺便把下载目录的真实路径
（从 shell folder 注册表读）写进 `data.js`，提示里显示完整路径并提供「复制路径」——
这是从这个位置能诚实做到的全部。

**MySlot 的导出串真的存在存档里。** `MyslotExports.exports[] = {name, value}`，所以关掉游戏也能
取出来——而这正是你需要它的时候。编辑模式那个 `edit-mode-cache-account.txt` 则**不是**导入串，
它是暴雪自己的缓存格式，粘不进任何地方，只能整份留着以后放回原路径。界面上这两者是分开标注的，
没有假装它们是一回事。

**滚动条：标准属性会让 `::-webkit-scrollbar` 整体失效。** 想把表格的横向滚动条加高，
写 `::-webkit-scrollbar { height: 18px }` 是对的，但如果同时设了 `scrollbar-width` 或
`scrollbar-color`（哪怕是在 `*` 上），Chromium 就切到标准渲染路径，所有 webkit 伪元素
规则连尺寸一起被忽略。实测：只有 webkit 规则 → 18px；再加 `scrollbar-width: thin` → 10px；
浏览器默认 → 15px。也就是说那条全局规则不但没生效，还把滚动条弄得比默认更细。
现在标准属性放在 `@supports not selector(::-webkit-scrollbar)` 里，只给 Firefox 用。

滚动条颜色用 `--accent` 混出来（`color-mix`），所以四种皮肤各有自己的滚动条颜色，
明暗切换也跟着走。自定义属性和 `color-mix` 在 `::-webkit-scrollbar-*` 里都能正常解析 ——
这点是截图采样实测的，不是猜的，所以不需要用 JS 去生成颜色。

**窗口几何记的是「还原后」的矩形，不是当前矩形。** 用 `GetWindowPlacement` 的
`rcNormalPosition` 加一个最大化标记。直接存最大化窗口的外框，下次会开出一个「和屏幕一样大
但不是最大化」的窗口，那不是同一件事。另外重开前检查一下矩形是否还落在虚拟屏幕内 ——
拔掉一个显示器之后，记住的位置可能在屏幕外。

**关闭看板的行为靠轮询窗口是否存在。** 网页没法通知启动器自己被关了（`beforeunload`
里做不了这种事），Chrome 的 app 模式窗口也不是我们的子进程。所以每 2 秒 `EnumWindows`
找一次那个窗口，从「在」变成「不在」就按设置处理。同一个轮询顺便把窗口几何存下来，
所以哪怕进程被强杀，位置也已经落盘了。

**自动重扫靠轮询，不靠文件通知。** 一开始只用 `FileSystemWatcher`，实测不可靠：改动时间戳
没有触发 `LastWrite` 事件，而且存档的写入方式不保证是「原地追加」（有 `.bak` 说明可能是
写新文件再改名，那样只会产生 FileName 事件）。所以现在以 **20 秒轮询 mtime+size** 为准，
文件通知只用来让常见情况反应更快。四个小文件的 stat 开销可以忽略。
另外 `FileSystemWatcher` 必须存在字段里 —— 只放局部变量的话方法一返回就可能被 GC 回收，
然后静默停止工作，这个坑我踩过一次。

  使用率之和中位数 72.9%、有 206 组不到 50% —— 剩下那些人穿的是什么不在数据里。
  面板每个部位标题上会显示「记录 xx%」，不到 50% 标黄，见「毕业装备」一节
* 毕业装备面板的图标是**打包前下好的**（`app/icons/`，462 张 56×56，约 1 MB），
  不是运行时去网上取。所以离线能看，但**换赛季出了新装备就得重新跑一次**
  `node tools\fetch-icons.js`（那一步需要能访问网络），见「毕业装备」一节
* ~~四个职业和三个专精的中文名显示为英文~~ **已修**：13 个职业 + 40 个专精
  全部取自暴雪 DB2（`app/class-names.js`），见「职业 / 专精中文名」一节
* 更新检查需要能访问 GitHub；国内网络经常访问不到，那时候只会静默跳过，不影响其它功能
* **窗口最外层那条标题栏（带最小化/最大化/关闭的那条）不受看板深浅和皮肤控制。**

  自己的外观设置**（Edge / Chrome → 设置 → 外观 → 深色），改那里才有用
* **标题栏和任务栏的字号同样改不了。** 那串字是 Chromium 用系统 UI 字体画的，

  设置 → 辅助功能 → 文本大小（或显示缩放），而它是全系统生效的，不是只影响这个程序。

**PowerShell 5.1 的编码陷阱，踩过三次，记在这里。** PS 5.1 读**没有 BOM** 的 `.ps1`
会按 ANSI（本机是 936）解码，里面的中文全毁。所以：

* `tools/*.ps1` 一律存成 **UTF-8 带 BOM**
* 需要传给 C# 编译器的中文，用 `\uXXXX` 注入，让生成的 `.cs` 保持纯 ASCII
  （`Add-Type` 写临时 `.cs` 用的是系统默认编码）
* **发布说明这类长中文文本，放到单独的 `.md` 文件里**，脚本用
  `[IO.File]::ReadAllText($p, [Text.UTF8Encoding]::new($false))` 读 ——
  v1.3.0 和 v1.3.1 的 Release 说明就是因为把中文写在无 BOM 的 `.ps1` 里而发成了乱码
